## What the Auditor Checks

The auditor verifies that you have a **documented, repeatable delivery methodology** for SAP-on-Azure engagements and that you actually use it — evidenced by project artefacts from a real customer.

**Typical questions:**

- What lifecycle do you use for SAP migrations / greenfield builds on Azure?
- Where is your SOW template? Is it standard across engagements?
- Can you show project artefacts (plan, RACI, status reports) from a recent engagement?

---

## Required Evidence Checklist

- [ ] **Documented delivery methodology** (lifecycle, phases, gates) — PDF / Word  
  _Explicitly call out SAP Activate phases (Discover → Prepare → Explore → Realize → Deploy → Run) mapped to your Azure workstream (landing zone, infrastructure build, cutover, hypercare). Cover phases, entry/exit criteria, gate reviews, and document control._
- [ ] **SOW or engagement contract template** — PDF / Word  
  _Include: scope, assumptions, dependencies, deliverables, acceptance criteria, change-control process, and pricing model placeholders._
- [ ] **Sample project plan / WBS** from a real engagement (anonymised) — PDF / Excel / MS Project
- [ ] **Sample status report / steering pack** — PDF / PowerPoint
- [ ] **RACI matrix** for a typical engagement — PDF / Excel

<Aside type="tip">
  Auditors want to see that the methodology is **alive** — provide artefacts from a recent customer
  engagement (anonymise the customer to "Customer A"). A plan, two status reports, a steering pack,
  and a sign-off email is a strong set.
</Aside>

## Common Gaps

- **Methodology exists but isn't SAP-aware:** add a one-page mapping to SAP Activate phases.
- **No real artefacts attached:** even one anonymised plan + one status report is enough.
- **Methodology is described in slides only:** convert to a versioned Word / PDF document.
